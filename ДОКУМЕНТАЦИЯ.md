# BrainPhotoTool — техническая документация

Программа обработки фото для лабораторного эксперимента (флуоресцентная
визуализация мышиных черепов/мозгов/срезов). Этот файл — техническое описание
устройства программы и история значимых решений, для разработки/отладки.
Пользовательская инструкция — отдельно, в `Как пользоваться.txt` (с сессии 6
лежит в репозитории, рядом с этим файлом).

путь и при копировании ломается).

При добавлении `программа/` в git-репозиторий обязательно добавлена в
`.gitignore` — она не version-control-friendly (сотни МБ бинарников).

## 2. Модель данных (`models.py`)

- `MaskMode` — `WHOLE_BLOB` (весь срез мозга целиком) или `ROSTRAL_CUT`
  (носовая/передняя часть черепа).
- `GroupConfig` — одна папка с фото одной группы животных: `mode`, `cols`
  (животных в ряд по горизонтали), `rows` (срезов на животное; `None` = определять
  автоматически по числу найденных пятен). С сессии 2 также `is_control` и
  `condition` (раздел 5.2).
- `Shot` — один кадр (набор файлов с разными выдержками одного и того же вида).
- `SpecimenMask` — маска одного животного/среза: растровая маска (`mask`,
  источник истины для площади/яркости), `accepted`, для `ROSTRAL_CUT`
  дополнительно `cut_line` (линия отреза, можно двигать в UI) и
  `source_blob`/`rostral_anchor` (для пересчёта маски при перетаскивании
  линии); с сессии 4 — `polygon` (вершины для режима точек, раздел 8.5).
  `animal_index`/`slice_index` — с 0 (в таблице результатов — с 1, раздел 12).
- `ShotReview` — кадр на проверке: `shot`, `image` (исходный dtype, по нему
  считается яркость), `display_image` (uint8 с растяжкой контраста, только для
  показа), `masks`, `warning`.
- `MeasurementRow` — одна строка измерений: `group`, `animal_index`,
  `slice_index`, `area_px`, `mean_intensity`, `std_intensity`, `source_file`,
  `mode`, `exposure_ms` (сессия 1, раздел 5), `is_control`, `condition`
  (сессия 2, раздел 5.2).

## 3. Сегментация (`segmentation.py`)

### 3.1. Обнаружение пятен — `detect_blobs()`

Единый строгий порог: медиана фона + `SEED_SIGMA_MULTIPLIER` (4.0) × устойчивый
разброс (MAD). Даёт уверенные "ядра" пятен — по их числу считается количество
животных/срезов на фото. Порог свой для каждого кадра (не Otsu на растянутой
гистограмме — тот отсекал тусклый диффузный край ткани вокруг ядра пятна на
флуоресцентных снимках).

### 3.2. Расширение до тусклого края — `grow_blob_to_soft_edge()`

Применяется ТОЛЬКО для `WHOLE_BLOB` (срезы), не для `ROSTRAL_CUT` (черепа —
геометрия чувствительна к форме пятна, см. 3.4).

У тусклых срезов сигнал плавно спадает к фону, и реальная граница ткани
(видна глазом, измеримо ещё повышена над фоном) оставалась за пределами
строгого порога — площадь занижалась, маска обрезала край. Решение —
гистерезис с ОГРАНИЧЕННЫМ радиусом роста:

1. Мягкий порог (`GROW_SIGMA_MULTIPLIER` = 1.5) — более щедрая маска.
2. `dilate(ядро, margin_px=15) ∩ мягкий_порог` — ядро расширяется до мягкого
   порога, но не дальше фиксированного радиуса вокруг себя.
3. Расширение других пятен на фото (`other_blobs`, тоже дилатированных на тот же
   `margin_px`) исключается из зоны роста — иначе спорная зона между двумя
   близкими срезами (тусклая "дымка" между ними выше мягкого порога — обычное
   дело для соседних срезов одного препарата) попадала бы в обе маски сразу
   и дублировала бы площадь/яркость. Симметричное исключение оставляет спорную
   полоску ничьей (консервативная недооценка), но без пересечения масок.

**Почему не просто гистерезисный порог по связности (без ограничения
радиуса)**: первая версия так и была сделана и сломалась на реальных фото —
мягкий порог местами недостаточно тёмный (неравномерная засветка/блики), и
маска "утекала" по связности через весь кадр в далёкий блик, разрастаясь на
треть кадра. Отсюда и ограничение фиксированным радиусом вместо чистой
связности.

### 3.3. Разделение черепов и мозгов — `assign_rostral_blobs_to_grid()` + `_split_by_largest_y_gap()`

На фото «череп и мозг» в одном кадре одновременно черепа (верхний ряд) и целые
мозги (нижний ряд) — в режиме `ROSTRAL_CUT` анализируются только черепа.

Наивный подход "взять самое верхнее пятно в каждой колонке" ломается, если у
одного черепа нос не прошёл порог (слишком тусклый) и не нашёлся как пятно —
тогда "самым верхним" в этой колонке оказывается мозг снизу.

Решение — сначала разделить ВСЕ пятна фото на верхнюю/нижнюю полосу по самому
большому разрыву по Y (`_split_by_largest_y_gap`), и только потом раскладывать
по колонкам внутри верхней полосы. Если черепа нет — колонка остаётся пустой
(доразметить вручную), а не подхватывает мозг.

Порог "заметности" разрыва — медиана ОСТАЛЬНЫХ разрывов (исключая сам
оцениваемый максимальный), умноженная на 2, минимум 30px. **Важно**: медиана
именно ОСТАЛЬНЫХ — если считать по всем разрывам включая оцениваемый, при
малом числе пятен (типично фото с одним животным, `cols=1`) медиана
самоотравляется и оказывается сопоставима с самим разрывом, из-за чего деление
почти никогда не срабатывает (баг, найденный код-ревью и исправленный).

Крайние случаи:
- **≥ 3 пятна** (≥ 2 разрывов) — медиана остальных разрывов работает надёжно.
- **Ровно 2 пятна** (типично `cols=1`) — сравнивать не с чем, делим безусловно
  (на фото «череп и мозг» с одним животным два пятна почти наверняка и есть
  пара череп+мозг).
- **1 пятно** — делить нечего; `assign_rostral_blobs_to_grid` в этом случае
  явно предупреждает пользователя ("не удалось надёжно отличить череп от
  мозга... проверьте вручную"), а не молча считает найденное пятно черепом.

Раньше сравнение шло с высотой (bbox по Y) пятна — оказалось ненадёжным:
черепа на реальных фото часто вытянуты почти на всю высоту своего ряда,
вплотную к границе с рядом мозгов (спинной мозг/срез уходит вниз), так что
высота пятна и разрыв между рядами — одного порядка величины.

### 3.4. Носовая часть черепа — `compute_rostral_cut()`

PCA по маске черепа → главная ось вытянутости → профиль ширины вдоль оси →
поиск "талии" между лицевым отделом и мозговой коробкой (`_find_rostral_boundary_bin`,
не менялась) → отрезаем всё до "талии" как носовую часть.

**Направление профиля** (какой конец считать носом) определяется знаком
Y-компоненты главной оси PCA (`main_axis[1] >= 0`) — по протоколу съёмки черепа
на этих фото ВСЕГДА лежат носом вверх (к меньшим Y на кадре). Это допущение
специфично для конкретного протокола этой лаборатории, не универсальный
алгоритм.

Раньше направление определялось сравнением средней ширины профиля в узком
окне (10% длины) на каждом конце — самый узкий конец считался носом. Ломалось,
если каудальный (задний) конец среза тоже сужался (например, если в кадр
попадает часть спинного мозга) — он мог оказаться ещё уже носа, и тогда почти
вся мозговая коробка ошибочно попадала в "носовую" обводку.

**Известное ограничение** (отмечено код-ревью как не блокирующее; в сессии 5
добавлено предупреждение, см. 9.1): если пятно почти круглое (собственные значения PCA близки —
блоб слабо вытянут, например из-за слияния/шума), направление главной оси
численно неустойчиво, и результат может быть случайным без предупреждения.
Также если реальный кадр нарушает протокол (череп положен не носом вверх) —
результат будет молча неверным для этого кадра. Дешёвая защита (warning при
`eigvals[largest]/eigvals[smallest]` близко к 1, и/или sanity-check против
старого способа по ширине) не реализована.

### 3.4.1. Длина линии отреза (фикс сессии 2)

`compute_rostral_cut` строила перпендикулярную линию отреза длиной 70% от
наибольшей стороны ВСЕГО кадра (`max(blob_mask.shape)`), а не от размера
самого черепа — `blob_mask` это маска размера всего фото (см. `Blob.mask`), и
на фото с несколькими животными в ряд один череп занимает малую долю кадра.
В результате концы линии у черепов ближе к краю кадра оказывались за
границами фото — пользователь не мог до них дотянуться мышью, чтобы
поправить.

Исправлено: длина считается от фактического разброса точек черепа поперёк
главной оси (перпендикулярной проекции), с запасом 20% на удобство хвата за
ручки, плюс дополнительный клип координат по границам фото на всякий случай.

### 3.5. `assign_blobs_to_grid()` (режим `WHOLE_BLOB`, срезы) — не менялась с сессии 1

Раскладывает пятна по сетке (животное × срез), число срезов на животное — по
умолчанию автоопределяется как максимум пятен в одном столбце.

## 4. Ручная доразметка (`canvas.py`)

`MaskCanvas` — виджет фото с полупрозрачными масками. Кисть (левая кнопка —
рисовать, правая — стирать, колесо — размер), для `ROSTRAL_CUT` дополнительно
линия отреза с двумя перетаскиваемыми ручками.

**Было**: линия отреза рисовалась и была перетаскиваемой только у активного
(выбранного) животного. На фото, где черепа лежат не по линейке, у остальных
животных линию было не видно и не поправить.

**Стало**: рисуются и перетаскиваемы ВСЕ линии сразу — активная ярко (толще,
непрозрачнее), остальные притушенно. Клик по ручке ЛЮБОЙ линии (не только
активной) сразу перетаскивает её и переключает активное животное — не нужно
сначала щёлкать по нему в списке слева.

### 4.1. Ластик (фикс сессии 2)

В боковой панели есть чекбокс «Ластик (стирать кистью, а не рисовать)», но
`MaskCanvas.mousePressEvent` безусловно перезаписывал режим кисти по кнопке
мыши (`erase_mode = event.button() == RightButton`) — чекбокс визуально
существовал, но ни на что не влиял. Это и была жалоба «ластик не работает»:
пользователь включал чекбокс и рисовал левой кнопкой, ожидая стирания.

Исправлено: добавлено независимое состояние `_erase_toggle`, чекбокс
подключён к `canvas.set_erase_enabled()`; итоговый режим — `_erase_toggle
ИЛИ правая кнопка мыши`. Правая кнопка по-прежнему стирает всегда, независимо
от чекбокса.

### 4.2. Кнопка «Принять всё на этом фото» подсвечивается зелёным

Кнопка загорается зелёным, когда на текущем фото не осталось непустых
непринятых масок, и гаснет при любой ручной правке — как кистью (это уже
сбрасывало `accepted`), так и перетаскиванием линии отреза для черепов (этот
путь раньше `accepted` не сбрасывал — несогласованность, исправлена заодно).
Механизм — ранее заведённый, но нигде не подключённый сигнал
`MaskCanvas.maskEdited` теперь слушается в `ReviewTab` и обновляет и список
животных (галочки «✓»), и стиль кнопки.

## 5. Результаты и статистика (`measurements.py`, `review_window.py`, `stats.py`)

### 5.1. Смешение режимов в сравнении групп (решено иначе в сессии 3, Блок 1)

Проблема: если пользователь добавляет в одном сеансе анализа И группу «череп и
мозг» (носовая площадь), И группу «срезы» (площадь среза) под ОДНИМ И ТЕМ ЖЕ
именем (разумный сценарий — анализ обоих этапов одного эксперимента разом),
их измерения — разные физические величины — молча усреднялись/сравнивались
вместе.

Исходное решение (сессия 1): `MeasurementRow` получил поле `mode`
(`whole_blob`/`rostral_cut`), `per_animal_average()` группировал и по `mode`
тоже, а в `ResultsTab` был выпадающий список "Что анализируем" для фильтрации
постфактум.

**Сессия 3, Блок 1**: постфактум-фильтр по режиму убран за ненадобностью —
теперь режим обводки фиксирован самим пайплайном (`PipelineTabs`, см. раздел
8.1), а не выбирается по группе, поэтому смешение режимов внутри одного цикла
Проект→Проверка→Результаты структурно невозможно. Поле `mode` в
`MeasurementRow` осталось (переносится как раньше, `per_animal_average`
по-прежнему группирует и по нему — само по себе безвредно и не требует
изменений), но выпадающий список "Что анализируем" в `ResultsTab` и метод
`_selected_mode`/`_mode_filtered` удалены.

### 5.2. Метка группы: контроль/опыт и произвольное условие (сессия 2)

`GroupConfig` получил два новых поля: `is_control` (фиксированный переключатель
«Контроль?» в таблице групп на вкладке «Проект») и `condition` (свободный
текст, например дата съёмки или «условие 2»). Оба переносятся в
`MeasurementRow` через `measure_shot()` и доживают до таблицы результатов
без изменений (как и `exposure_ms`, не участвуют в ключе группировки
`per_animal_average`).

В `ResultsTab` добавлен выпадающий список **«Сравнивать по»**:
- «Группе (как есть)» — прежнее поведение, без изменений;
- «Контроль vs Опыт» — колонка `group` перед сравнением подменяется на
  `is_control` (`True` → «Контроль», `False` → «Опыт»); несколько физических
  групп с одинаковой меткой объединяются в одну сторону сравнения;
- «Условию (все со всеми)» — колонка `group` подменяется на `condition`;
  строки с пустым условием исключаются. При 3+ уникальных значениях условия
  `compare_groups` сам делает Краскела-Уоллиса + попарные сравнения с
  поправкой Холма — отдельно это реализовывать не пришлось, функция уже
  поддерживает произвольное число групп.

Подмена происходит ПОСЛЕ агрегации по животным (`per_animal_average`), то есть
пул наблюдений для каждой физической группы считается как обычно, а
объединение под общей меткой — только на уровне финального сравнения.

### 5.3. Сравнение групп на одной и той же выдержке (сессия 2)

Раньше единственная реакция на разную выдержку между группами — предупреждение
постфактум в тексте результата сравнения (см. 5.4). Пользователь пояснил
практический сценарий: в папке группы всегда лежит несколько файлов с разной
выдержкой на один кадр (имя файла содержит `exp<число>`, парсится в
`imaging.py`), и для сравнения групп нужно явно взять ОДНУ и ту же выдержку
для всех групп режима (например, все «срезы» на 250мс, все «черепа» на
150мс) — а не полагаться на то, что автовыбор `choose_best_exposure()`
(наибольшая незасвеченная выдержка) случайно совпадёт между группами.

Так как `Shot.exposure_files` и раньше хранил пути ко ВСЕМ вариантам выдержки
кадра (не только к автоматически выбранному), решение не потребовало
пересчёта масок — геометрия маски не зависит от того, каким файлом выдержки
она была найдена, меняются только значения яркости под теми же пикселями:

- `measure_shot()` теперь принимает необязательные `image`/`exposure_ms` —
  если не заданы, поведение как раньше (автовыбор кадра); если заданы,
  считает те же принятые маски по другому изображению того же кадра.
- В `ResultsTab` добавлен выпадающий список «Выдержка для сравнения»,
  заполняемый выдержками, ОБЩИМИ для всех кадров текущего режима
  (пересечение множеств `exposure_files.keys()`). При выборе конкретной
  выдержки таблица и статистика пересчитываются по ней; кадры, у которых
  файла с такой ровно выдержкой нет, исключаются с явным списком под
  таблицей — молчаливого исключения нет.
- Пункт «Авто» сохраняет прежнее поведение по умолчанию.

**Ограничение**: сопоставление по выдержке точное (совпадение числа `exp` в
имени файла), без допуска — если фактическая выдержка отличается на
единицу (например, `exp249` и `exp250` у разных групп из-за ручной
установки в разных сессиях съёмки), общего варианта в списке не будет.

### 5.4. Несопоставимая выдержка между группами

`choose_best_exposure()` выбирает "лучшую" незасвеченную выдержку для КАЖДОГО
кадра независимо — если сравниваемые группы были сфотографированы на разной
выдержке, яркостные метрики (`mean_intensity`/`std_intensity`) могут быть
искажены (дольше выдержка — систематически выше сигнал), даже без реального
биологического различия.

Решение: `MeasurementRow` получил поле `exposure_ms` (из `shot.chosen_exposure`).
При сравнении групп по яркостной метрике, если у сравниваемых групп разный
набор выдержек — в вывод добавляется явное предупреждение с конкретными
значениями выдержки по каждой группе. Для `area_px` предупреждение не
показывается (площадь исторически считалась менее чувствительной к экспозиции
за счёт адаптивного порога, но это не строго доказано — заявление не делается).

## 7. Известные ограничения / что не сделано

- **Разметка не сохраняется на диск.** `ReviewTab.reviews` живёт только в
  памяти: закрытие программы (или повторный «Начать проверку масок» с
  подтверждением) теряет всю проверку. Для одной группы это минуты, для
  нескольких групп с ручной обводкой эпителия — часы работы. Кандидат на
  следующую сессию: сохранять маски (например, `.npz` рядом с данными или
  проект-файл) и загружать при старте. Не сделано — нужен формат, который
  переживёт изменения кода между сессиями, это стоит обсудить с пользователем.
- ~~Общий редизайн UX ручной доразметки (навигация/зум)~~ — зум/пан сделаны в
  сессии 4 (8.5.1), превью кисти и заметная активная маска — в сессии 6 (10).
  Горячих клавиш для переключения животных по-прежнему нет (не запрашивались).
- `compute_rostral_cut`: нет sanity-проверки против нарушения протокола (череп
  положен не носом вверх на конкретном кадре) — см. раздел 3.4. Автовыделение
  носовой части по-прежнему грубое эвристикой (PCA + "талия" по профилю
  ширины) — в сессии 2 по прямому запросу пользователя чинилась только
  геометрия линии (не улетает за кадр), сам алгоритм поиска границы не
  менялся. **Уточнение сессии 5**: защита от слабо вытянутых (почти круглых)
  пятен частично сделана (раздел 9) — есть явное предупреждение "проверьте
  вручную", сам алгоритм направления по-прежнему PCA (числовая неустойчивость
  на почти круглых пятнах не устранена, только обозначена пользователю).
- ~~Правка точками теряет несвязные области маски~~ — исправлено в сессии 6
  (раздел 10, `apply_polygon_edit`). Остаётся: **дырки** внутри маски
  (`RETR_EXTERNAL`) полигон заливает при первой правке точками. На реальных
  автомасках всех 4 групп дырок нет (проверено в сессии 6), поэтому оставлено
  как есть; станет важно, если появятся срезы с желудочками/разрывами ткани,
  которые нужно исключать из площади.
- Круговое преобразование маска → полигон → маска (первая правка точками)
  меняет площадь на реальных масках до ~1% даже у неправленых краёв
  (упрощение контура до 40 вершин, `POLYGON_MAX_POINTS`) — в пределах точности
  ручной обводки, но стоит помнить при сравнении «до/после» правки.
- ~~`_build_composite_rgb` пересобирается на каждый `paintEvent`~~ — исправлено
  в сессии 6 (кеш + bbox, раздел 10).
- `grow_blob_to_soft_edge` пересчитывает фон (blur/медиану/MAD) по всему кадру
  для КАЖДОГО пятна отдельно — избыточная работа при многих срезах на фото;
  не критично при типичных размерах фото, но можно вынести наружу и посчитать
  один раз на кадр.
- Утверждение "площадь не зависит от экспозиции" не подтверждено строго
  (адаптивный порог снижает, но не гарантированно устраняет зависимость) —
  предупреждение о разной выдержке сейчас показывается только для яркостных
  метрик; сравнение на зафиксированной выдержке (раздел 5.3) не решает эту
  проблему для площади, только для яркости.
- Список выдержек для сравнения (раздел 5.3) сопоставляет ТОЧНОЕ число из
  имени файла — если в разных группах выдержка отличается на единицу-две
  из-за ручной установки в разных сессиях съёмки, общий вариант не появится
  в списке (округление/допуск не реализованы).
- Общая точность автоматических масок (не только носовой части черепа, но и
  срезов) осталась как есть — в сессии 2 пользователь просил починить именно
  ластик и геометрию линии отреза, не трогая сам алгоритм распознавания
  контура. **Уточнение сессии 3**: этого оказалось недостаточно — см. раздел
  8, там же зафиксирована новая жалоба на ластик (возможно, другой сценарий,
  не тот же баг) и на общее неудобство ручной доразметки.

- **Известное ограничение**: при >8 групп палитра неизбежно повторяется

- `stats_output.setPlainText(...)` заменён на `setHtml(_format_stats_html(lines))`.

**Проверено** точечным скриптом на headless Qt (`QT_QPA_PLATFORM=offscreen`,

### 8.5. Полигон точек — MVP (сделано в сессии 4, вне очереди)

Причина вне очереди: пользователь сообщил, что человек прямо сейчас вручную
выделяет фото в ImageJ вместо программы — кисть оказалась настолько неудобной,
что делает программу непригодной к работе, и это важнее, чем всё остальное в
плане. Кроме того, всплыло новое требование, которого не было при исходном
планировании Блока 4: обонятельный эпителий — не прямой отрез, а анатомическая
полость сложной вогнутой формы ("запятая"), которую в принципе нельзя честно
выделить простым геометрическим алгоритмом (PCA-разрез и т.п.). Вместо двух
разных решений (полигон для правки срезов + отдельный алгоритм формы для
эпителия) сделано ОДНО: полигон работает поверх ЛЮБОЙ текущей растровой маски
независимо от пайплайна — для срезов это точечная правка неплохой автомаски,
для эпителия — способ обвести сложную форму вручную, но быстро (вогнутости
полигон поддерживает, кисть для них крайне неудобна). Вопрос "как показать
критерии" полости отложен осознанно: алгоритм не пытается угадать границу
полости, инструмент даёт точный ручной контроль.

**Решение по развилке из исходного плана**: полигон — второй режим, СОСУЩЕСТВУЕТ
с кистью (не заменяет). Переключатель "Режим точек" в боковой панели
(`ReviewTab`), кисть при этом не рисует (весь ввод мыши уходит на работу с
точками), но остаётся доступна переключением обратно.

Файлы: `models.py` (`SpecimenMask.polygon`), `segmentation.py`
(`mask_to_polygon`, `polygon_to_mask`), `canvas.py` (весь интерактив),
`review_window.py` (`ReviewTab` — чекбокс + подсказка).

- `SpecimenMask.polygon: list[tuple[float, float]] | None` — вершины по кругу
  в координатах изображения; `None` = маска как раньше, чисто растровая.
  Растровая `mask` остаётся источником истины для площади/яркости
  (`measurements.py` не менялся вообще) — полигон только способ её
  РЕДАКТИРОВАТЬ, при любом изменении вершин сразу растеризуется обратно.
- `mask_to_polygon()` — отправная точка контура: `cv2.findContours` (самый
  большой контур, если их несколько) + `cv2.approxPolyDP` с увеличивающимся
  эпсилон, пока число вершин не уложится в `POLYGON_MAX_POINTS` (40, оценка на
  глаз — не измерялась на реальных фото). Пустая маска (нечего обводить) →
  `None`, полигон не строится. `polygon_to_mask()` — обратно, `cv2.fillPoly`.
- `MaskCanvas`: `_point_mode_enabled` — при включении (или при загрузке нового
  фото, пока режим включён) вызывается `_ensure_all_polygons()` — строит
  полигон из текущей растровой маски для КАЖДОЙ маски на фото, у кого его ещё
  нет (лениво, один раз на маску).
  - Перетаскивание вершины: как и `cut_line` раньше — во время движения
    растеризация НЕ идёт (только контур-превью), `mask` пересчитывается один
    раз на отпускании кнопки (`mouseReleaseEvent`), тогда же сбрасывается
    `accepted` (та же логика, что и у кисти/`cut_line`).
  - Двойной клик на ребре — добавляет вершину (`_hit_test_polygon_edge_any`,
    порог `EDGE_HIT_RADIUS_PX`, точка вставляется сразу, без ожидания
    отпускания). Одиночный клик мимо вершины в режиме точек НАМЕРЕННО ничего
    не делает — иначе случайный клик рядом с ребром при попытке просто
    попасть по вершине было бы неотличимо от намеренного добавления точки.
  - Правая кнопка по вершине — удаляет её (`len(polygon) > 3`, чтобы не
    схлопнуть полигон до вырожденного).
  - Рисование кистью сбрасывает `polygon` в `None` (как и `cut_line`/
    `source_blob` раньше) — маска "отвязывается" от векторного представления;
    при повторном включении режима точек полигон перестроится заново уже по
    подправленному кистью растру.
- **Известные ограничения MVP** (сознательно не в первой версии, см. также
  раздел 7):
  - Явного индикатора "это ребро — попадёт двойной клик" на канвасе нет,
    только сама линия контура.
  - Обонятельный эпителий по-прежнему живёт в `MaskMode.ROSTRAL_CUT` (свой
    `MaskMode` из раздела 8.3 не заведён) — начальный контур для полигона в
    этом режиме берётся из авто-обрезанной по прямой линии носовой части
    (`compute_rostral_cut`), а не с нуля; для формы-"запятой" это разумная
    отправная точка (обрезать лишнее проще, чем обвести с нуля), но не
    идеальная.

**Проверено** точечными скриптами на headless Qt (`QT_QPA_PLATFORM=offscreen`):
`mask_to_polygon`/`polygon_to_mask` на окружности и на вогнутой форме
(полумесяц) — расхождение площади после конвертации в обе стороны <2% и <5%
соответственно; перетаскивание вершины через реальные `QMouseEvent`
(`mousePressEvent`/`mouseMoveEvent`/`mouseReleaseEvent`) — маска не меняется
во время движения, меняется и растёт при отпускании; двойной клик на
середине ребра добавляет ровно одну вершину; ПКМ по вершине удаляет её;
рисование кистью сбрасывает полигон в `None`; пустая маска не порождает
полигон. Отдельно пересобран `BrainPhotoTool.exe` (PyInstaller) и проверено,
что стартует без падения — как из `dist/`, так и из рабочей `программа/`.

- **Полигон только у активной маски** оказался реальной проблемой, не
  теоретическим ограничением: переключение между животными/срезами в списке
  слева "работает отвратительно". Решено показывать и делать перетаскиваемыми
  полигоны ВСЕХ масок сразу — `_ensure_all_polygons()` строит контур для
  каждой маски на фото, `paintEvent`/`mousePressEvent`/`mouseDoubleClickEvent`
  перебирают все маски (не только активную), в точности по схеме, ранее
  сделанной для `cut_line`: активная — ярче (alpha 230, толщина 2, ручки 5px),
  остальные — притушены (alpha 110, толщина 1, ручки 3px). Попадание по
  вершине/ребру ЛЮБОЙ маски (не только активной) сразу переключает активное
  животное на неё — щёлкать по списку слева больше не обязательно.
- **Нельзя приблизить фото** — без зума нельзя было понять, легли ли точки
  полигона на реальный край ткани или нет ("непонятно, норм они или нет").
  Добавлены `_zoom`/`_pan_offset` в `MaskCanvas`, встроенные в существующую
  геометрию `_recompute_draw_rect`/`_screen_to_image` без изменения их API —
  `_scale` теперь `base_scale * zoom`, а центрирующее смещение сдвинуто на
  `_pan_offset`, поэтому весь остальной код (хит-тесты, отрисовка), уже
  работающий через `_scale`/`_draw_rect`, зум не заметил и не потребовал
  правок. Управление: **Ctrl + колесо** — зум с заякориванием под курсором
  (точка фото под мышью не съезжает при масштабировании — стандартное
  поведение просмотрщиков, реализовано через `_zoom_at`: сначала переводим
  экранную точку курсора в координаты фото ДО смены зума, потом после смены
  зума считаем, куда она делась на экране, и компенсируем разницу через
  `_pan_offset`). **Средняя кнопка мыши (зажать+вести)** — панорама, не
  занимает ни левую/правую кнопку (кисть/полигон), ни колесо (кисть/зум).
  Зум зажат в `[1.0, 8.0]`; обычное колесо без Ctrl по-прежнему меняет
  размер кисти, как и раньше. Новое фото (`set_shot`) сбрасывает зум/пан —
  иначе после смены кадра увеличенный фрагмент предыдущего фото сбивал бы с
  толку. Это же закрывает пункт 1 Блока 5 (раздел 8.4) — сделано раньше
  очереди по той же причине срочности, что и сам полигон.
- **График сравнения хотелось видеть сразу, а не только сохранять в файл** —
  раньше единственным способом увидеть боксплот было "Сохранить график..." во
  внешний PNG. Теперь `stats.py::_build_boxplot_figure` вынесена как общая
  отрисовка для `save_boxplot` (в файл, без изменений) и новой
  `boxplot_png_bytes` (в PNG-байты в памяти) — не два дублирующих друг друга
  куска кода. В `ResultsTab` под текстом сравнения справа появился `QLabel`
  с превью графика (масштабируется под размер, `Qt.AspectRatioMode.KeepAspectRatio`),
  заполняется в `_run_comparison()` тем же вызовом, что раньше использовался
  только для `_save_plot()` — те же группы, тот же title-суффикс
  (`_plot_title_suffix()`, общий для обоих мест). При недостатке данных или
  ошибке сравнения показывается плейсхолдер (`_clear_plot_preview()`) вместо
  графика от предыдущего запуска — иначе можно было бы принять устаревший
  график за актуальный.

**Проверено** точечными скриптами на headless Qt: полигоны строятся у ОБЕИХ
масок синтетического двухживотного кадра сразу (не только у активной); клик
по вершине неактивной маски переключает активную маску на неё; Ctrl+колесо
увеличивает зум и `_scale`, обычное колесо без Ctrl зум не трогает (меняет
только кисть); зум зажат в `[1.0, 8.0]`; средняя кнопка двигает `_pan_offset`
на величину движения мыши 1:1; смена фото сбрасывает зум и пан в исходное.
Отдельно — `ResultsTab`: до сравнения на месте графика плейсхолдер без
пиксмапы; после `_run_comparison()` появляется непустой PNG; при откате к
одной группе (недостаточно данных) плейсхолдер возвращается, а не остаётся
старый график. Полный `MainWindow` (2 пайплайна × 3 вкладки) пересобран и
проверен без регрессий. Exe пересобран (PyInstaller), запущен из `dist/` и из
рабочей `программа/` — стартует без падения.

### 9.1. Выделение носа/эпителия (`canvas.py`, `segmentation.py`)

**Критично — в режиме точек (по умолчанию включён для пайплайна носа) клик
мимо вершины не делал ничего вообще, если у маски ещё нет полигона** —
`mousePressEvent` для пустой ячейки (авто-детекция не нашла череп, штатный
случай раздела 3.3) просто возвращался без действия, а кисть в режиме точек
отключена полностью. Такую ячейку было физически невозможно нарисовать без
выключения "Режима точек" — при дефолтном состоянии пайплайна носа пользователь
об этом переключателе мог и не вспомнить. Исправлено (`mousePressEvent`):
если у активной маски ещё нет `polygon` (нечего обвести контуром), клик мимо
вершины теперь рисует кистью как обычно — полигон сам перестроится по
получившемуся растру при следующей отрисовке, и дальше маску можно
доправить уже точками.

**Высокий — простой показ кадра (не правка!) стирал `cut_line`/`source_blob`
при включённом режиме точек** — `_ensure_polygon` вызывалась эагерно из
`set_shot`/`paintEvent` для ВСЕХ масок кадра просто чтобы их отрисовать, и
безусловно обнуляла `cut_line`/`source_blob` попутно. Поскольку режим точек
включён по умолчанию для пайплайна носа (раздел 8.5.3), это происходило ещё
до того, как пользователь вообще посмотрел на кадр — вся механика
"перетащить простую линию отреза" (`recompute_rostral_mask_from_line`)
становилась мёртвым кодом для этого пайплайна при дефолтных настройках, даже
если пользователь тут же выключал "Режим точек" обратно, рассчитывая на
линию. Исправлено: `_ensure_polygon` больше не трогает `cut_line`/
`source_blob` — это чисто отображение временного контура, не правка.
Отвязка от линии теперь происходит только при РЕАЛЬНОЙ правке точками
(перетаскивание/добавление/удаление вершины — как и раньше уже отвязывает
кисть), симметрично сохранённому поведению. Чтобы не задваивать картинку
(линия отреза поверх контура полигона), ручки `cut_line` теперь не рисуются,
пока включён режим точек (`paintEvent`) — в этом режиме они и раньше не
реагировали на клик, только визуально мешали.

**Высокий — "Пересчитать автоматически заново" стирал всю ручную правку без
подтверждения**, в отличие от перехода Next/Prev (`_confirm_leave_unaccepted`).
Добавлено подтверждение (`ReviewTab._recompute_current`) — диалог показывается,
только если на кадре есть хоть одна непустая маска (иначе нечего терять).

**Средний — вырожденная линия отреза (обе ручки сведены в одну точку) отдавала
весь череп под "нос" молча.** `direction = p2 - p1` становится нулевым
вектором, и `side >= 0` истинно для всех точек blob — `recompute_rostral_mask_from_line`
возвращала весь `source_blob` без ошибки/предупреждения. Исправлено в
`canvas.py::mouseReleaseEvent`: при вырожденной линии (обе точки ближе 1px)
пересчёт маски просто пропускается (маска остаётся прежней) — пользователь
должен развести ручки снова, а не получить тихо неверный результат.

**Средний (частично) — PCA-направление неустойчиво на почти круглых пятнах**
(раздел 7). Полноценного решения (другой алгоритм) не делалось — добавлено
дешёвое явное предупреждение: `compute_rostral_cut` возвращает третьим
элементом `is_elongated` (соотношение собственных значений PCA `>= 1.5`),
`build_masks_for_image` собирает список животных с `is_elongated=False` и
добавляет предупреждение в уже существующий канал (`ShotReview.warning`,
показывается в `ReviewTab.warning_label`) — "проверьте направление линии
вручную", без блокировки автоматического предложения.

**Низкий — двойной клик точно по существующей вершине полигона создавал рядом
дублирующую вырожденную точку** (реальная последовательность Qt-событий:
Press на первом клике уже начинает `_dragging_polygon_vertex`, второй клик
триггерит `mouseDoubleClickEvent`, а хит-тест ребра засчитывал клик у самого
конца ребра как "попадание в середину"). Исправлено в
`_hit_test_polygon_edge_any`: клик ближе `EDGE_HIT_RADIUS_PX` к любому из
концов ребра больше не считается кандидатом на вставку точки.

**Найдено, не исправлено** (добавлено в раздел 7 как известное ограничение):
потеря несвязных компонент маски при первой правке точками; отсутствие
кеширования `_build_composite_rgb` (подтормаживание на больших фото при
активной правке).

### 9.2. Выгрузка таблиц и статистика (`measurements.py`, `stats.py`, `nonparametric.py`, `ResultsTab`)

**Критично — экспорт таблицы/графика при недоступном пути падал ПОЛНОСТЬЮ
МОЛЧА**: ни диалога об ошибке, ни диалога "Готово". Подтверждено эмпирически
(реальный клик по кнопке, не прямой вызов метода): `_export_table`/
`_save_plot` не оборачивали `export_table`/`save_boxplot` в try/except;
исключение (файл открыт в Excel, диск недоступен) гасится где-то на границе
диспетчера сигналов Qt, а exe собран без консоли (`console=False`) — stderr
пользователю не виден вообще. Пользователь решал, что данные сохранены, хотя
файла нет. Исправлено — оба места обёрнуты в try/except с `QMessageBox.warning`
(тот же паттерн, что уже был у `_run_comparison`/`compare_groups`).

**Средний — таблица на экране и экспортируемый файл могли отличаться по
порядку строк.** `_refresh_table` присваивала `self.current_df = df` ДО
сортировки, которая происходила локально внутри `_show_dataframe` (не
затрагивая `self.current_df`). Исправлено: сортировка перенесена в
`_refresh_table` до присвоения `self.current_df`, `_show_dataframe` больше не
сортирует повторно — теперь это гарантированно один и тот же порядок.

**Средний — точный тест Манна-Уитни мог упасть `RecursionError` на сильно
несбалансированных выборках.** `_mannwhitney_exact_p`: рекурсия `count()`
глубиной ~`n1+n2` (не ~`n1*n2`), а порог перехода на точный тест
(`_EXACT_LIMIT`) проверял только `n1*n2`. Подтверждено: `n1=2, n2=1250`
(`n1*n2=2500`, ровно на старом пороге) падало с `RecursionError` при лимите
рекурсии Python по умолчанию (1000). В реальном использовании инструмента это
достижимо: единица "животное" — это `(group, mode, source_file,
animal_index)` (раздел 5.1, `per_animal_average`), то есть КАЖДОЕ фото даёт
свой независимый набор животных — при накоплении многих фото по одной группе
число строк легко становится большим и несбалансированным. Исправлено:
добавлен отдельный порог `_EXACT_MAX_TOTAL_N = 500` на `n1+n2` — при
превышении используется нормальное приближение (уже существующая, корректная
ветка), как и предусматривалось комментарием в коде для "больших выборок".

**Средний — CSV-экспорт не открывался напрямую в русском Excel.** `,` как
разделитель колонок и `.` как десятичный (pandas-дефолт) в русской локали
Excel даёт один столбец A и текстовые (не числовые) значения яркости/площади
при двойном клике по файлу. Исправлено: CSV-ветка `export_table` теперь
использует `sep=";"`, `decimal=","` (Excel-экспорт `.xlsx` не затронут — там
такой проблемы нет).

### 9.3. Общая надёжность (`main.py`, `imaging.py`, `review_window.py`)

### 10.3. Правка точками не теряет несвязные куски маски (`segmentation.apply_polygon_edit`)

Закрыто ограничение из раздела 7 (найдено ревью сессии 5). При правке точками
(перетаскивание/добавление/удаление вершины) маска теперь =

пересекающиеся со старым полигоном. Компонента, которую полигон представлял,
заменяется новым контуром целиком, как и раньше. Для перетаскивания старый
полигон запоминается на нажатии (`_drag_polygon_before`), т.к. во время
движения `m.polygon` уже меняется. На реальных данных сценарий редкий:
автомаски всех 4 групп — одна связная область без дырок (проверено скриптом
по всем кадрам), несколько кусков появляются только от мазков кистью до
включения режима точек.

  пустой активной маски — см. 9.1), и не показывается во время панорамы/
  перетаскивания ручек. Курсор отслеживается в `mouseMoveEvent`, сбрасывается
  в `leaveEvent`.
- **Активная маска** — контрастная обводка (чёрная подложка 3.5px + белая
  1.5px, `cv2.findContours(RETR_LIST)` — видны и дырки, кеш по объекту маски)

  животного их несколько, как в списке слева). В режиме точек обводка не

### 10.5. Кеш отрисовки (`canvas.py`)

Закрыто ограничение из раздела 7. Превью кисти требует перерисовки на каждое
движение мыши, а `paintEvent` пересобирал наложение масок по всему кадру —
без кеша превью сделало бы программу заметно медленнее. Три уровня:
1. `_composite_pixmap_cached` — готовая QPixmap, ключ = (объект фото,
   `active_key`, кортеж (объект `m.mask`, индексы) по всем маскам), сравнение
   через `is`. Корректно, потому что ВСЕ правки масок в программе
   переприсваивают `m.mask` новым массивом (кисть — `mask | brush`, полигон —
   `apply_polygon_edit`, линия — `recompute_rostral_mask_from_line`, пересчёт —
   новый список масок), а не меняют на месте. **Если когда-нибудь появится
   правка на месте (`m.mask[...] = ...`) — кеш её не увидит**; тогда нужно
   сбрасывать `_composite_key = None`.
2. `_base_rgb` — серое фото в float-RGB, один раз на кадр.
3. `_mask_bbox` — смешивание каждой маски только внутри её bbox.

Замер на реальном кадре 1368×918 с 30 срезами: перерисовка при движении
курсора — 11 мс; при мазке кистью (меняется одна маска) — ~22 мс против
250–540 мс раньше. Результат композита сверен со старой реализацией
пиксель-в-пиксель на всех кадрах одной группы (срезы и черепа).

### 12.2. Сравнение групп (`stats.compare_groups`, `nonparametric.py`)

- Единица анализа — животное (таблица по животным или один выбранный срез),
  никогда не отдельный срез (псевдоповторность).
- 2 группы — двусторонний Манн-Уитни. Без повторов значений и при
  n1·n2 ≤ 2500, n1+n2 ≤ 500 — точное распределение U; иначе нормальное
  приближение с поправкой на повторы и на непрерывность.
- 3+ группы — Краскел-Уоллис (с поправкой на повторы) + попарные Манн-Уитни с
  поправкой Холма (показываются и сырые, и скорректированные p).
- Размер эффекта — ранговая бисериальная корреляция `1 − 2U/(n1·n2)`, от −1 до
  +1.
- Минимально достижимое p при данных n1, n2 — `2 / C(n1+n2, n1)`; если оно
  ≥ 0.05, выводится предупреждение («незначимо» ≠ «эффекта нет»).
- **Сверка со scipy/statsmodels (сессия 6)**: 400 случайных наборов (n от 2
  до 30, с повторами и без, 2–5 групп). Максимальное расхождение p: точный
  Манн-Уитни 2·10⁻¹⁴, асимптотический 2·10⁻¹⁶ (`scipy.stats.mannwhitneyu`,
  `use_continuity=True`), Краскел-Уоллис 4·10⁻¹⁰ (`scipy.stats.kruskal`), Холм
  — точное совпадение (`statsmodels multipletests(method="holm")`); значения U
  совпадают. Для раздела «методы» статьи можно писать «критерий Манна-Уитни /
  Краскела-Уоллиса, поправка Холма» — реализация эквивалентна scipy.
