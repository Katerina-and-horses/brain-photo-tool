# BrainPhotoTool — техническая документация

Программа обработки фото для лабораторного эксперимента (флуоресцентная
визуализация мышиных черепов/мозгов/срезов). Этот файл — техническое описание
устройства программы и история значимых решений, для разработки/отладки.
Пользовательская инструкция — отдельно, в `Как пользоваться.txt`.

## 1. Структура проекта

```
brainphoto/
  данные/                         — сырые фото по исследованиям (не код)
    README.md                     — конвенция раскладки папок для новых исследований
    <исследование>/
      <группа>/{голова, череп и мозг, срезы}/*.tif+*.xml
      результаты/                 — сводные таблицы/графики по исследованию
  brain_photo_tool/                — этот репозиторий
    src/braintool/                 — исходный код
    app_entry.py, BrainPhotoTool.spec, requirements.txt  — сборка PyInstaller
    программа/                     — готовая exe-сборка (gitignored, ~468 МБ)
    Запуск программы.lnk           — ярлык на программа/BrainPhotoTool.exe
    Как пользоваться.txt           — инструкция для не-программиста
```

`данные/` и `brain_photo_tool/` разведены сознательно: данные не должны попадать
в git, а готовая exe-сборка не должна путаться с сырыми фото. Ярлык и инструкция
лежат прямо в `brain_photo_tool/`, чтобы папку можно было передать не-специалисту
целиком («тыкай ярлык»).

При добавлении `программа/` в git-репозиторий обязательно добавлена в
`.gitignore` — она не version-control-friendly (сотни МБ бинарников).

## 2. Модель данных (`models.py`)

- `MaskMode` — `WHOLE_BLOB` (весь срез мозга целиком) или `ROSTRAL_CUT`
  (носовая/передняя часть черепа).
- `GroupConfig` — одна папка с фото одной группы животных: `mode`, `cols`
  (животных в ряд по горизонтали), `rows` (срезов на животное; `None` = определять
  автоматически по числу найденных пятен).
- `Shot` — один кадр (набор файлов с разными выдержками одного и того же вида).
- `SpecimenMask` — маска одного животного/среза: растровая маска, для
  `ROSTRAL_CUT` дополнительно `cut_line` (линия отреза, можно двигать в UI) и
  `source_blob`/`rostral_anchor` (для пересчёта маски при перетаскивании линии).
- `MeasurementRow` — одна строка измерений: `group`, `animal_index`,
  `slice_index`, `area_px`, `mean_intensity`, `std_intensity`, `source_file`,
  **`mode`** и **`exposure_ms`** (добавлены в этой сессии — см. раздел 5).

## 3. Сегментация (`segmentation.py`)

### 3.1. Обнаружение пятен — `detect_blobs()`

Единый строгий порог: медиана фона + `SEED_SIGMA_MULTIPLIER` (4.0) × устойчивый
разброс (MAD). Даёт уверенные "ядра" пятен — по их числу считается количество
животных/срезов на фото. Порог свой для каждого кадра (не Otsu на растянутой
гистограмме — тот отсекал тусклый диффузный край ткани вокруг ядра пятна на
флуоресцентных снимках).

### 3.2. Расширение до тусклого края — `grow_blob_to_soft_edge()`

Применяется ТОЛЬКО для `WHOLE_BLOB` (срезы), не для `ROSTRAL_CUT` (черепа —
геометрия чувствительна к форме пятна, см. 3.4).

У тусклых срезов сигнал плавно спадает к фону, и реальная граница ткани
(видна глазом, измеримо ещё повышена над фоном) оставалась за пределами
строгого порога — площадь занижалась, маска обрезала край. Решение —
гистерезис с ОГРАНИЧЕННЫМ радиусом роста:

1. Мягкий порог (`GROW_SIGMA_MULTIPLIER` = 1.5) — более щедрая маска.
2. `dilate(ядро, margin_px=15) ∩ мягкий_порог` — ядро расширяется до мягкого
   порога, но не дальше фиксированного радиуса вокруг себя.
3. Расширение других пятен на фото (`other_blobs`, тоже дилатированных на тот же
   `margin_px`) исключается из зоны роста — иначе спорная зона между двумя
   близкими срезами (тусклая "дымка" между ними выше мягкого порога — обычное
   дело для соседних срезов одного препарата) попадала бы в обе маски сразу
   и дублировала бы площадь/яркость. Симметричное исключение оставляет спорную
   полоску ничьей (консервативная недооценка), но без пересечения масок.

**Почему не просто гистерезисный порог по связности (без ограничения
радиуса)**: первая версия так и была сделана и сломалась на реальных фото —
мягкий порог местами недостаточно тёмный (неравномерная засветка/блики), и
маска "утекала" по связности через весь кадр в далёкий блик, разрастаясь на
треть кадра. Отсюда и ограничение фиксированным радиусом вместо чистой
связности.

### 3.3. Разделение черепов и мозгов — `assign_rostral_blobs_to_grid()` + `_split_by_largest_y_gap()`

На фото «череп и мозг» в одном кадре одновременно черепа (верхний ряд) и целые
мозги (нижний ряд) — в режиме `ROSTRAL_CUT` анализируются только черепа.

Наивный подход "взять самое верхнее пятно в каждой колонке" ломается, если у
одного черепа нос не прошёл порог (слишком тусклый) и не нашёлся как пятно —
тогда "самым верхним" в этой колонке оказывается мозг снизу.

Решение — сначала разделить ВСЕ пятна фото на верхнюю/нижнюю полосу по самому
большому разрыву по Y (`_split_by_largest_y_gap`), и только потом раскладывать
по колонкам внутри верхней полосы. Если черепа нет — колонка остаётся пустой
(доразметить вручную), а не подхватывает мозг.

Порог "заметности" разрыва — медиана ОСТАЛЬНЫХ разрывов (исключая сам
оцениваемый максимальный), умноженная на 2, минимум 30px. **Важно**: медиана
именно ОСТАЛЬНЫХ — если считать по всем разрывам включая оцениваемый, при
малом числе пятен (типично фото с одним животным, `cols=1`) медиана
самоотравляется и оказывается сопоставима с самим разрывом, из-за чего деление
почти никогда не срабатывает (баг, найденный код-ревью и исправленный).

Крайние случаи:
- **≥ 3 пятна** (≥ 2 разрывов) — медиана остальных разрывов работает надёжно.
- **Ровно 2 пятна** (типично `cols=1`) — сравнивать не с чем, делим безусловно
  (на фото «череп и мозг» с одним животным два пятна почти наверняка и есть
  пара череп+мозг).
- **1 пятно** — делить нечего; `assign_rostral_blobs_to_grid` в этом случае
  явно предупреждает пользователя ("не удалось надёжно отличить череп от
  мозга... проверьте вручную"), а не молча считает найденное пятно черепом.

Раньше сравнение шло с высотой (bbox по Y) пятна — оказалось ненадёжным:
черепа на реальных фото часто вытянуты почти на всю высоту своего ряда,
вплотную к границе с рядом мозгов (спинной мозг/срез уходит вниз), так что
высота пятна и разрыв между рядами — одного порядка величины.

### 3.4. Носовая часть черепа — `compute_rostral_cut()`

PCA по маске черепа → главная ось вытянутости → профиль ширины вдоль оси →
поиск "талии" между лицевым отделом и мозговой коробкой (`_find_rostral_boundary_bin`,
не менялась) → отрезаем всё до "талии" как носовую часть.

**Направление профиля** (какой конец считать носом) определяется знаком
Y-компоненты главной оси PCA (`main_axis[1] >= 0`) — по протоколу съёмки черепа
на этих фото ВСЕГДА лежат носом вверх (к меньшим Y на кадре). Это допущение
специфично для конкретного протокола этой лаборатории, не универсальный
алгоритм.

Раньше направление определялось сравнением средней ширины профиля в узком
окне (10% длины) на каждом конце — самый узкий конец считался носом. Ломалось,
если каудальный (задний) конец среза тоже сужался (например, если в кадр
попадает часть спинного мозга) — он мог оказаться ещё уже носа, и тогда почти
вся мозговая коробка ошибочно попадала в "носовую" обводку.

**Известное ограничение** (не исправлено, отмечено код-ревью как не
блокирующее): если пятно почти круглое (собственные значения PCA близки —
блоб слабо вытянут, например из-за слияния/шума), направление главной оси
численно неустойчиво, и результат может быть случайным без предупреждения.
Также если реальный кадр нарушает протокол (череп положен не носом вверх) —
результат будет молча неверным для этого кадра. Дешёвая защита (warning при
`eigvals[largest]/eigvals[smallest]` близко к 1, и/или sanity-check против
старого способа по ширине) не реализована.

### 3.4.1. Длина линии отреза (фикс сессии 2)

`compute_rostral_cut` строила перпендикулярную линию отреза длиной 70% от
наибольшей стороны ВСЕГО кадра (`max(blob_mask.shape)`), а не от размера
самого черепа — `blob_mask` это маска размера всего фото (см. `Blob.mask`), и
на фото с несколькими животными в ряд один череп занимает малую долю кадра.
В результате концы линии у черепов ближе к краю кадра оказывались за
границами фото — пользователь не мог до них дотянуться мышью, чтобы
поправить.

Исправлено: длина считается от фактического разброса точек черепа поперёк
главной оси (перпендикулярной проекции), с запасом 20% на удобство хвата за
ручки, плюс дополнительный клип координат по границам фото на всякий случай.

### 3.5. `assign_blobs_to_grid()` (режим `WHOLE_BLOB`, срезы) — не менялась в этой сессии

Раскладывает пятна по сетке (животное × срез), число срезов на животное — по
умолчанию автоопределяется как максимум пятен в одном столбце.

## 4. Ручная доразметка (`canvas.py`)

`MaskCanvas` — виджет фото с полупрозрачными масками. Кисть (левая кнопка —
рисовать, правая — стирать, колесо — размер), для `ROSTRAL_CUT` дополнительно
линия отреза с двумя перетаскиваемыми ручками.

**Было**: линия отреза рисовалась и была перетаскиваемой только у активного
(выбранного) животного. На фото, где черепа лежат не по линейке, у остальных
животных линию было не видно и не поправить.

**Стало**: рисуются и перетаскиваемы ВСЕ линии сразу — активная ярко (толще,
непрозрачнее), остальные притушенно. Клик по ручке ЛЮБОЙ линии (не только
активной) сразу перетаскивает её и переключает активное животное — не нужно
сначала щёлкать по нему в списке слева.

### 4.1. Ластик (фикс сессии 2)

В боковой панели есть чекбокс «Ластик (стирать кистью, а не рисовать)», но
`MaskCanvas.mousePressEvent` безусловно перезаписывал режим кисти по кнопке
мыши (`erase_mode = event.button() == RightButton`) — чекбокс визуально
существовал, но ни на что не влиял. Это и была жалоба «ластик не работает»:
пользователь включал чекбокс и рисовал левой кнопкой, ожидая стирания.

Исправлено: добавлено независимое состояние `_erase_toggle`, чекбокс
подключён к `canvas.set_erase_enabled()`; итоговый режим — `_erase_toggle
ИЛИ правая кнопка мыши`. Правая кнопка по-прежнему стирает всегда, независимо
от чекбокса.

### 4.2. Кнопка «Принять всё на этом фото» подсвечивается зелёным

Кнопка загорается зелёным, когда на текущем фото не осталось непустых
непринятых масок, и гаснет при любой ручной правке — как кистью (это уже
сбрасывало `accepted`), так и перетаскиванием линии отреза для черепов (этот
путь раньше `accepted` не сбрасывал — несогласованность, исправлена заодно).
Механизм — ранее заведённый, но нигде не подключённый сигнал
`MaskCanvas.maskEdited` теперь слушается в `ReviewTab` и обновляет и список
животных (галочки «✓»), и стиль кнопки.

## 5. Результаты и статистика (`measurements.py`, `review_window.py`, `stats.py`)

### 5.1. Смешение режимов в сравнении групп

Проблема: если пользователь добавляет в одном сеансе анализа И группу «череп и
мозг» (носовая площадь), И группу «срезы» (площадь среза) под ОДНИМ И ТЕМ ЖЕ
именем (разумный сценарий — анализ обоих этапов одного эксперимента разом),
их измерения — разные физические величины — молча усреднялись/сравнивались
вместе.

Решение: `MeasurementRow` получил поле `mode` (`whole_blob`/`rostral_cut`).
`per_animal_average()` группирует и по `mode` тоже (не только по группе/кадру/
животному). В `ResultsTab` добавлен выпадающий список **"Что анализируем"**,
заполняется по факту присутствующих в загруженных данных режимов — таблица и
статистика сравнения ВСЕГДА фильтруются по выбранному режиму перед
агрегацией/сравнением.

### 5.2. Метка группы: контроль/опыт и произвольное условие (сессия 2)

`GroupConfig` получил два новых поля: `is_control` (фиксированный переключатель
«Контроль?» в таблице групп на вкладке «Проект») и `condition` (свободный
текст, например дата съёмки или «условие 2»). Оба переносятся в
`MeasurementRow` через `measure_shot()` и доживают до таблицы результатов
без изменений (как и `exposure_ms`, не участвуют в ключе группировки
`per_animal_average`).

В `ResultsTab` добавлен выпадающий список **«Сравнивать по»**:
- «Группе (как есть)» — прежнее поведение, без изменений;
- «Контроль vs Опыт» — колонка `group` перед сравнением подменяется на
  `is_control` (`True` → «Контроль», `False` → «Опыт»); несколько физических
  групп с одинаковой меткой объединяются в одну сторону сравнения;
- «Условию (все со всеми)» — колонка `group` подменяется на `condition`;
  строки с пустым условием исключаются. При 3+ уникальных значениях условия
  `compare_groups` сам делает Краскела-Уоллиса + попарные сравнения с
  поправкой Холма — отдельно это реализовывать не пришлось, функция уже
  поддерживает произвольное число групп.

Подмена происходит ПОСЛЕ агрегации по животным (`per_animal_average`), то есть
пул наблюдений для каждой физической группы считается как обычно, а
объединение под общей меткой — только на уровне финального сравнения.

### 5.3. Сравнение групп на одной и той же выдержке (сессия 2)

Раньше единственная реакция на разную выдержку между группами — предупреждение
постфактум в тексте результата сравнения (см. 5.4). Пользователь пояснил
практический сценарий: в папке группы всегда лежит несколько файлов с разной
выдержкой на один кадр (имя файла содержит `exp<число>`, парсится в
`imaging.py`), и для сравнения групп нужно явно взять ОДНУ и ту же выдержку
для всех групп режима (например, все «срезы» на 250мс, все «черепа» на
150мс) — а не полагаться на то, что автовыбор `choose_best_exposure()`
(наибольшая незасвеченная выдержка) случайно совпадёт между группами.

Так как `Shot.exposure_files` и раньше хранил пути ко ВСЕМ вариантам выдержки
кадра (не только к автоматически выбранному), решение не потребовало
пересчёта масок — геометрия маски не зависит от того, каким файлом выдержки
она была найдена, меняются только значения яркости под теми же пикселями:

- `measure_shot()` теперь принимает необязательные `image`/`exposure_ms` —
  если не заданы, поведение как раньше (автовыбор кадра); если заданы,
  считает те же принятые маски по другому изображению того же кадра.
- В `ResultsTab` добавлен выпадающий список «Выдержка для сравнения»,
  заполняемый выдержками, ОБЩИМИ для всех кадров текущего режима
  (пересечение множеств `exposure_files.keys()`). При выборе конкретной
  выдержки таблица и статистика пересчитываются по ней; кадры, у которых
  файла с такой ровно выдержкой нет, исключаются с явным списком под
  таблицей — молчаливого исключения нет.
- Пункт «Авто» сохраняет прежнее поведение по умолчанию.

**Ограничение**: сопоставление по выдержке точное (совпадение числа `exp` в
имени файла), без допуска — если фактическая выдержка отличается на
единицу (например, `exp249` и `exp250` у разных групп из-за ручной
установки в разных сессиях съёмки), общего варианта в списке не будет.

### 5.4. Несопоставимая выдержка между группами

`choose_best_exposure()` выбирает "лучшую" незасвеченную выдержку для КАЖДОГО
кадра независимо — если сравниваемые группы были сфотографированы на разной
выдержке, яркостные метрики (`mean_intensity`/`std_intensity`) могут быть
искажены (дольше выдержка — систематически выше сигнал), даже без реального
биологического различия.

Решение: `MeasurementRow` получил поле `exposure_ms` (из `shot.chosen_exposure`).
При сравнении групп по яркостной метрике, если у сравниваемых групп разный
набор выдержек — в вывод добавляется явное предупреждение с конкретными
значениями выдержки по каждой группе. Для `area_px` предупреждение не
показывается (площадь исторически считалась менее чувствительной к экспозиции
за счёт адаптивного порога, но это не строго доказано — заявление не делается).

## 6. Хронология этой рабочей сессии

1. **Реорганизация файлов** — разрозненные папки (`срезы`, `brain_photo_tool`,
   `Обработка фото мозга`) сведены в `brainphoto/{данные, brain_photo_tool}`.
   Добавлен `README.md` с конвенцией для будущих исследований.
2. **Первый раунд фиксов** (коммит `c518df2`): все линии отреза видны/
   перетаскиваемы (раздел 4); мозги исключены из анализа на фото «череп и
   мозг» (первая версия — "самое верхнее пятно в колонке"); гистерезисный
   порог для тусклых срезов (первая версия — по связности, без ограничения
   радиуса).
3. **Пользователь протестировал и сообщил о регрессиях**: блики на срезах,
   черепа выделяются "полностью", статистика "странная" (смешение), выдержка
   между группами разная.
4. **Второй раунд фиксов**: диагностика на реальных фото всех 4 групп лаборатории
   (не на одном примере — ключевой урок первого раунда), рост маски ограничен
   радиусом (раздел 3.2), разделение по Y-полосам вместо "верхнее пятно в
   колонке" (раздел 3.3, первая версия), направление носа по PCA-оси вместо
   ширины (раздел 3.4), поля `mode`/`exposure_ms` и фильтр в `ResultsTab`
   (раздел 5).
5. **Независимое код-ревью** (агент "Программист") нашло 2 реальных бага в
   правках раунда 4 ДО того, как они дошли до пользователя:
   - критично: медиана разрывов в `_split_by_largest_y_gap` самоотравлялась
     при малом числе пятен — именно тот случай, ради которого писалась защита;
   - важно: `grow_blob_to_soft_edge` исключал только ядро соседнего пятна, не
     его расширение — спорная зона между близкими срезами дублировалась в
     обеих масках (пересечение 80px на тесте ревью).
   Оба исправлены (коммит `f4d4f50`), перепроверены на тех же тестах, что
   использовал ревьюер (пересечение масок → 0px), плюс полный повторный
   прогон по всем 4 группам без регрессий.
6. Exe пересобран (PyInstaller), запущен и проверен (стартует без падения,
   ярлык рабочий).
7. **Сессия 2** (по замечаниям пользователя после практического использования):
   - починен ластик — чекбокс "Ластик" был не подключён ни к чему (раздел 4.1);
   - линия отреза черепа больше не улетает за границы кадра — длина считается
     от размера самого черепа, а не всего фото (раздел 3.4.1);
   - перетаскивание линии отреза теперь тоже сбрасывает "принято" у маски,
     как и правка кистью (раньше — несогласованность, раздел 4.2);
   - кнопка "Принять всё на этом фото" подсвечивается зелёным, пока правок
     не было (раздел 4.2);
   - метка группы "Контроль/Опыт" + произвольное условие (например, дата) —
     сравнение "все со всеми" по этой метке в результатах (раздел 5.2);
   - сравнение групп можно явно зафиксировать на одной выдержке (раздел 5.3).
   Изменения проверены точечными скриптами (не полноценные автотесты — их в
   проекте нет): геометрия линии отреза на синтетическом черепе у края кадра,
   сброс `accepted` при перетаскивании ручки, работа ластика через чекбокс на
   headless Qt, перенос `exposure_ms`/`is_control`/`condition` через
   `measure_shot`/`per_animal_average`.

## 7. Известные ограничения / что не сделано

- Общий редизайн UX ручной доразметки (навигация/зум при рисовании кистью) —
  из исходного списка задач пользователя, отложен на будущее.
- `compute_rostral_cut`: нет защиты от слабо вытянутых (почти круглых) пятен
  и нет sanity-проверки против нарушения протокола (череп положен не носом
  вверх на конкретном кадре) — см. раздел 3.4. Автовыделение носовой части
  по-прежнему грубое эвристикой (PCA + "талия" по профилю ширины) — в сессии 2
  по прямому запросу пользователя чинилась только геометрия линии (не улетает
  за кадр), сам алгоритм поиска границы не менялся.
- `grow_blob_to_soft_edge` пересчитывает фон (blur/медиану/MAD) по всему кадру
  для КАЖДОГО пятна отдельно — избыточная работа при многих срезах на фото;
  не критично при типичных размерах фото, но можно вынести наружу и посчитать
  один раз на кадр.
- Утверждение "площадь не зависит от экспозиции" не подтверждено строго
  (адаптивный порог снижает, но не гарантированно устраняет зависимость) —
  предупреждение о разной выдержке сейчас показывается только для яркостных
  метрик; сравнение на зафиксированной выдержке (раздел 5.3) не решает эту
  проблему для площади, только для яркости.
- Список выдержек для сравнения (раздел 5.3) сопоставляет ТОЧНОЕ число из
  имени файла — если в разных группах выдержка отличается на единицу-две
  из-за ручной установки в разных сессиях съёмки, общий вариант не появится
  в списке (округление/допуск не реализованы).
- Общая точность автоматических масок (не только носовой части черепа, но и
  срезов) осталась как есть — в сессии 2 пользователь просил починить именно
  ластик и геометрию линии отреза, не трогая сам алгоритм распознавания
  контура. **Уточнение сессии 3**: этого оказалось недостаточно — см. раздел
  8, там же зафиксирована новая жалоба на ластик (возможно, другой сценарий,
  не тот же баг) и на общее неудобство ручной доразметки.

## 8. План дальнейшей работы (сессия 3)

После практического использования (сессия 2 фиксов) пользователь обнаружил,
что текущая архитектура упирается в потолок сразу по нескольким осям.
Зафиксирован план на несколько будущих сессий — ниже порядок и содержание
каждого блока. Эта сессия — только планирование, код не менялся.

**Зафиксированные пользователем решения**:
- Два пайплайна ("срезы" и "обонятельный эпителий") — ПОЛНОСТЬЮ раздельные
  циклы Проект→Проверка→Результаты, каждый со своим списком групп/фото, без
  общего хранилища и без фильтра по режиму постфактум.
- «Обонятельный эпителий» — тот же анатомический регион, что сейчас
  называется «носовая часть черепа» (`MaskMode.ROSTRAL_CUT`), просто нужен
  другой алгоритм выделения формы и явное разделение на стороны.
- Левая/правая половина эпителия — раздельные строки измерений, помеченные
  номером животного, чтобы их можно было объединить в статистике позже
  (НЕ склеивать автоматически).
- Переход кисти на контур точками (векторный полигон) — обсуждать отдельно,
  начиная с оценки стоимости и изолированного прототипа, не тотальной заменой
  сразу.

**Порядок сессий**: Блок 1 → Блок 2+3 → Блок 4 → Блок 5 (Блок 1 меняет
верхнеуровневую архитектуру, на которую опирается всё остальное).

### 8.1. Блок 1 — два раздельных пайплайна

Файлы: `review_window.py` (`MainWindow`, `ProjectTab`, `ReviewTab`,
`ResultsTab`), `models.py::GroupConfig`/`MaskMode`.

- `MainWindow` получает два полностью независимых цикла — свой список
  `self.reviews` на каждый, без общего хранилища.
- `ProjectTab`: убрать выбор режима "Что обводить" из таблицы групп — режим
  фиксирован самим пайплайном.
- `ResultsTab`: убрать `mode_combo` ("Что анализируем", ныне ~строки
  355-358, 435-449, 503-513) — фильтрация по mode больше не нужна.
- `per_animal_average`/`compare_groups` уже mode-агностичны, менять не
  требуется.
- **Развилка (решить в начале сессии)**: единое окно с двумя верхними
  вкладками vs стартовый экран выбора пайплайна с двумя независимыми окнами
  — оба варианта разумны.

### 8.2. Блок 2+3 — сравнение по срезу + читаемая группировка/график

Сравнение по номеру среза (`measurements.py::per_animal_average`,
`ResultsTab._animal_df`/`_run_comparison`):
- `slice_index` уже присваивается по позиции сверху вниз в столбце
  (`segmentation.py::_split_into_columns`), но `per_animal_average`
  схлопывает его в ключе группировки — нужен режим "по конкретному срезу
  №N" рядом с текущим "среднее по животному", опции строить динамически по
  фактически найденным `slice_index`. Явно показывать, сколько животных
  выпало при выбранном N.
- Допущение для фиксации: порядок среза на фото (сверху вниз) = анатомический
  порядок, без дополнительной сверки — достаточно для первой итерации.

Читаемая группировка/график (`stats.py::save_boxplot`,
`ResultsTab._show_dataframe`):
- Жалоба не про отсутствие данных (группы реально передаются в
  `compare_groups`/`tick_labels=groups`), а про то, что визуально это не
  бросается в глаза — один серый цвет точек на все группы, нет легенды.
- Перед правкой графика — свериться с навыком/гайдлайнами `dataviz` проекта,
  не выбирать палитру самостоятельно.
- Раскрасить боксы/точки по группам, подписать n на оси X, визуально
  сгруппировать строки таблицы результатов по group; рассмотреть `setHtml`
  вместо `setPlainText` в текстовом выводе сравнения для выделения p-value.

### 8.3. Блок 4 — обонятельный эпителий: новый алгоритм + лево/право

Файлы: `models.py` (`MaskMode`, `SpecimenMask`, `MeasurementRow`),
`segmentation.py` (новая функция рядом с `compute_rostral_cut`),
`measurements.py::per_animal_average`, `canvas.py`, `review_window.py`.

- Отдельное значение `MaskMode` для эпителия (не переиспользовать
  `ROSTRAL_CUT` с доп. флагом).
- `SpecimenMask` получает поле `side: "left"/"right"/None`; идентификатор
  активной маски в `canvas.py` (`active_key`, сейчас пара
  `(animal_index, slice_index)`) расширяется до тройки с `side` — правки
  нужны везде, где ключ используется (поиск активной маски, список
  животных, drag ручек).
- `MeasurementRow` получает поле `side`; `per_animal_average` включает его в
  ключ группировки, чтобы лево/право НЕ усреднялись автоматически;
  `ResultsTab` получает переключатель "лево/право отдельно / объединить" —
  простая доп. агрегация поверх `side`.
- Алгоритм автомаски — гипотеза, не решение: переиспользовать PCA-логику
  `compute_rostral_cut` для нахождения ростральной зоны, затем внутри неё
  искать продольную линию симметрии геометрически (не по яркости — асимметрия
  яркости может быть самим измеряемым эффектом). Линия раздела —
  перетаскиваемая, по аналогии с уже существующим `recompute_rostral_mask_from_line`
  (разрезать blob линией, оставить сторону — механизм переиспользуется
  напрямую).
- **Обязательный шаг перед кодом**: посмотреть на реальные фото эпителия под
  этим углом и проверить гипотезу алгоритма — отдельной съёмки под эпителий
  в данных нет (`данные/README.md`: только голова/череп и мозг/срезы), это
  тот же кадр черепа.
- `build_masks_for_image` для этого mode генерирует ДВЕ `SpecimenMask` на
  ячейку сетки; для физически отсутствующей половины — пустая маска (как
  сейчас для пустых ячеек сетки).

### 8.4. Блок 5 — ручная доразметка

По возрастанию риска — сначала точечные фиксы, полигон в конце как отдельное
обсуждение и прототип, не тотальная замена сразу.

1. **Зум/пан при рисовании** (`canvas.py::_recompute_draw_rect`,
   `_screen_to_image` — сейчас всегда вписывают всё фото целиком). Развести
   жесты с уже занятым колесом мыши (сейчас колесо = размер кисти).
2. **Курсор-превью размера кисти** (`_paint_brush`) — сейчас размер кисти не
   визуализируется до клика.
3. **Активная маска малозаметна** (`_build_composite_rgb` — разница всего
   0.7 против 0.55 alpha) — усилить контуром/подписью на канвасе.
4. **Неудобное переключение животных** (`ReviewTab._rebuild_animal_list`) —
   горячие клавиши и/или выбор маски прямым кликом по фото.
5. **"Ластик не стирает автомаску" — перепроверить заново, НЕ считать
   исправленным**: чекбоксный баг из сессии 2 в текущем коде выглядит
   рабочим (`erase_mode = self._erase_toggle or ПКМ`), значит жалоба,
   вероятно, про другой сценарий (например, первое движение кистью обнуляет
   `cut_line`/`source_blob` и меняет поведение маски — раздел 4.1/4.2). Нужен
   отдельный шаг воспроизведения на реальных данных перед правкой, а не
   повторное слепое исправление того же самого.
6. **Кисть → контур точками (полигон)** — самое рискованное решение,
   обсуждается отдельно, НЕ реализуется сразу целиком:
   - Контур — добавка поверх растровой маски (нужна растеризация через
     `cv2.fillPoly` для подсчёта площади/яркости), не замена модели данных.
   - Механизм перетаскиваемых вершин уже частично есть как прообраз в виде
     ручек `cut_line` (`_draw_handles`/`_dragging_handle`) — переиспользовать
     архитектурно.
   - Риски: сложные топологии (дыры, разрыв пятна бликом на 2 части) полигон
     не поддерживает нативно, растровая маска — поддерживает; регрессия
     скорости работы для тех, кто привык к кисти.
   - Порядок действий: сначала обсудить с пользователем — заменяет ли полигон
     кисть полностью или сосуществует как второй режим ("кисть для грубой
     правки + полигон для точной обводки"), затем изолированный прототип на
     одном тестовом фото, и только потом интеграция.
